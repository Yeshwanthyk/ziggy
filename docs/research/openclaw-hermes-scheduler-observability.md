## Ziggy fit (recommendation, not source evidence)

Ziggy already has resident Telegram, Discord, and Slack loops in `src/application/gateway.ts`, `discord-gateway.ts`, and `slack-gateway.ts`. The scheduler can run beside those loops. A public `ziggy scheduler run <profile>` can host the same loop when no channel gateway is running.

This removes all scheduler-owned launchd and systemd work. Ziggy does not need to install, restart, repair, or inspect an OS service. An operator who wants boot-time startup can supervise a Ziggy gateway or `scheduler run` with any external process manager.

Because more than one gateway can run for a Profile, each tick must take one short Profile-local tick lock. The durable occurrence claim remains the final duplicate barrier.

Borrow the smallest common mechanism, not either product's full cron system:

1. Persist one `nextRunAt` cursor for each schedule.
2. Give each due occurrence a stable identity from `automationId + scheduleDigest + scheduledFor`.
3. In one transaction, insert the occurrence record and advance `nextRunAt` **before** gate, model, or delivery effects. A uniqueness constraint on the occurrence identity is the claim.
4. Record `claimed`, `running`, then one immutable terminal result: `completed`, `failed`, `skipped-gate`, `skipped-busy`, `missed`, or `unknown`.
5. If several slots elapsed while no host was alive, advance to the next future slot and write one `missed` range with its first slot, last slot, and count. Never replay that range.
6. If a process ends after claim but before a terminal write, mark the attempt `unknown` after its run lock is known to be released. Never replay it.
7. Keep bounded error and output summaries in the ledger. Keep full Pi session output in Pi's existing session store.

The operator surface can stay small:

- `ziggy scheduler status <profile>` — last tick, ticker freshness, next due slot, active run, and counts for recent failed, skipped, missed, and unknown outcomes.
- `ziggy scheduler runs <profile> [automation]` — newest-first occurrence history with run ID, scheduled time, status, start, duration, and bounded reason.
- `ziggy scheduler tick <profile>` — perform one portable tick.
- `ziggy scheduler run <profile>` — run the same ticker in the foreground.

`status` is read-only. It reports a stale ticker when `lastTickAt` is older than the declared tick interval plus tolerance. It reports disagreement as unknown or stale rather than trying repeated reads to manufacture certainty.

## Conclusion

Both systems put ordinary scheduling inside an already resident Gateway. OS services supervise the Gateway; they are not part of scheduler correctness. OpenClaw has the richer operator-facing task/run model. Hermes has the clearest small audit primitive: an immutable execution ledger that distinguishes `claimed`, `running`, terminal failure, and restart-ambiguous `unknown`.

Ziggy can host one portable ticker inside its existing gateways or a foreground command. A persisted next occurrence, transactional consume-before-dispatch claim, immutable occurrence ledger, missed-range record, and read-only status surface provide the required no-replay behavior and honest observability without launchd, systemd, generation fencing, drift repair, or a startup-fuse database.
